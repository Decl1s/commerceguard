# CG-204: два времени и объяснимая корректировка истории

25.10.2026, `0.1.0.dev9`. Я написал этот срез без запуска приложения, импорта,
SQL, миграций, CLI и проверок. Примеры и ожидаемые ответы ниже — рассуждения по
контракту, а не наблюдённые результаты. У проекта по-прежнему статус unverified.

## Что я считаю бизнес-задачей

Я хочу ответить на два разных вопроса финансового специалиста. Первый: «Почему
вчера в отчёте была недостача?» Второй: «С учётом поступивших позже данных,
каким был результат за вчера?» Перезапись вчерашней таблицы дала бы удобную
текущую сумму, но лишила бы меня объяснения вчерашнего решения. Подстановка
вчерашнего observed_at позднему факту создала бы ложную историю знания.

Поэтому я сохраняю оба отчёта и связываю корректировку с опубликованным baseline.
У каждого run собственные immutable входы, времена, reason и fingerprint движка.
Я сравниваю сохранённые результаты отдельным read-only запросом. Пересчёт не
означает перевод денег, подтверждение бухгалтерской проводки или удаление кейса.

## Какие временные оси я разделяю

| Поле | Как я его использую |
| --- | --- |
| `occurred_at` PSP | Когда произошла платёжная операция; сравниваю с business cutoff |
| `observed_at` receipt | Когда источник сообщает о знании факта; сравниваю с knowledge cutoff |
| `effective_at` OMS | С какой бизнес-даты действует полный снимок ожиданий |
| `observed_at` OMS | Когда снимок стал известен источнику |
| `published_at` batch | Технический маркер публикации принятого пакета; ограничиваю им входы |
| `as_of` run | Конец рассматриваемого бизнес-состояния |
| `knowledge_at` run | Самая поздняя допустимая граница знания для этого отчёта |

Я использую aware datetime и нормализую время в UTC. Для точных контрактов сохраняю
RFC3339 с шестью десятичными знаками и Z. Сравнение строк в произвольных часовых
поясах не заменяет сравнение моментов времени. `knowledge_at` не может быть раньше
`as_of` и не может лежать в будущем относительно часов БД при prepare.

Я сохраняю важное ограничение CG-201: published_at выставляется до COMMIT и не
является точным PostgreSQL commit timestamp. Фраза «было известно» здесь относится
к объявленному контракту source observed + published marker. Точное воспроизведение
я получаю через уже сохранённые input IDs. Поздний новый prepare со старой границей
не доказывает, какой именно MVCC snapshot видел процесс в прошлом.

## Как я задаю режим

В `as-was` я требую `knowledge_at=as_of`; если knowledge не указан, принимаю эту
же границу. Видимость PSP: `occurred_at<=as_of AND observed_at<=knowledge_at`.
В `as-known-now` сохраняю прежний business cutoff и явно задаю более позднее знание.
Слово now не означает скрытый вызов часов: фактический knowledge_at передаю явно,
чтобы повтор одной команды не зависел от времени следующего запуска.

Для as-known-now я требую baseline_run_id опубликованного результата того же
магазина и того же as_of, с меньшим knowledge_at. Это может быть исходный as-was
или предыдущая корректировка. Причину выбираю из `manual`, `scheduled`,
`late-data`, `recovery`. В свободное поле легко случайно вставить контакт или
содержимое документа, поэтому такой текст я пока не принимаю. `late-data` и
baseline не разрешаю в as-was; для обычного запуска reason по умолчанию manual.

В manifest v2 я записываю request с reason/baseline, visibility_version
`occurred-observed-v2`, оба времени и прежнюю knowledge_basis. Полный canonical
JSON входит в run_key, а значит, в UUIDv5. Те же входы/параметры/код дают тот же
manifest; другая причина также меняет identity запроса. Я не выдаю prepare за
завершённое выполнение — result появляется только в отдельном execute.

## Как я выбираю входы

Я выбираю последний полный OMS по effective_at<=as_of и observed_at<=knowledge_at,
из опубликованных к knowledge_at пакетов. При равных effective/observed разных
снимков отказываю как при неоднозначном источнике. Корректировка может выбрать
новый поздно сообщённый OMS, который действует на старую бизнес-дату. CG-205
отдельно займётся версией ожиданий и разделением сроков capture/refund.

Для PSP я закрепляю опубликованные пакеты с manifest observed_at<=knowledge_at.
Затем kernel ограничивает реальные события по occurred/receipt observed. Пакет
может содержать события вне business cutoff; я не вырезаю их из raw и не делаю
вид, что все его строки вошли в денежную сумму. Пределы 10000 OMS и 50000 receipts
для вычисления сохраняю. До измерений я не обещаю конкретную скорость.

Равные semantic PSP факты из разных пакетов остаются receipts, дедупликацию
выполняю по merchant/event. Я не снимаю запрет CG-103 на более раннее observed_at
у повторно принятого canonical event. Исправление первой даты знания — отдельная
задача миграции данных; эту историю нельзя тихо переписать ради красивого отчёта.

## Где я меняю поведение

| Файл | Что я написал | Почему |
| --- | --- | --- |
| `domain.py`, `reconcile.py` | knowledge_at в результате; две независимые границы фильтра | Kernel не должен подменять время позднего факта |
| `run_plans.py` | Manifest v2, reason/baseline, выбор OMS/PSP по знанию | Я фиксирую полный набор до вычисления |
| `run_execution.py` | Контракт v1/v2, result v2, видимость receipt в evidence | Я объясняю не только наличие сырой строки, но и её участие |
| `run_changes.py` | Сравнение двух immutable результатов и newly visible refs | Просмотр различий не пересчитывает kernel |
| `case_store.py` | Явный CASE_CORRECTION_REPORT_ONLY | Историческая корректировка не двигает текущую карточку |
| `0007_temporal_corrections.sql` | Расширение checks, reason/baseline FK, result_version | Старые строки и миграции я не обновляю |

Я изменил байты kernel/selector, поэтому engine SHA изменится. Старый manifest
сохранит свой fingerprint. В новом checkout его execute откажет при несовпадении,
а сохранённые show/result/evidence останутся читаемыми. Для повторного вычисления
старой версии мне понадобится соответствующий checkout и совместимая схема;
универсального исторического исполнителя я пока не написал. Переименование версии
ruleset не заменяет версию реализации: balance-v1 по-прежнему описывает смысл
правил сумм, visibility_version — контракт знания, SHA — конкретные исходники.

## Как я прохожу через позднюю оплату

Я беру заказ с expected_capture=10000. До T0 опубликовано 9000 capture. Исходный
R1: as_of=T0, knowledge=T0, as-was, finding shortfall=-1000. Затем приходит PSP
capture 1000 с occurred_at<T0 и observed_at>T0. Я принимаю его как новый пакет,
сохраняя исходные времена и raw. В T1 после публикации создаю R2: as_of=T0,
knowledge=T1, as-known-now, baseline=R1, reason=late-data.

В R2 я ожидаю actual=10000 и отсутствие прежнего finding. R1 остаётся прежним.
Если occurred_at был бы после T0, я не включил бы эту операцию даже при knowledge=T1:
поздняя доставка и новое бизнес-событие — разные причины изменения состояния.
Если поздно пришёл OMS с новыми ожиданиями, отличие также может происходить из OMS,
а newly_visible_event_count будет нулевым. Я показываю добавленные/убранные input IDs
и оставляю run evidence для разбора конкретного заказа.

## Как я читаю отличие

`run changes` берёт baseline из сохранённого manifest. Я сравниваю findings по
case_key и возвращаю appeared/disappeared/changed/unchanged counts, bounded пары
before/after, добавленные и убранные inputs. У unchanged finding в двух run могут
быть разные raw receipts; изменение входов показываю отдельно от изменения сумм.

Я также возвращаю впервые видимые относительно baseline event IDs и их receipt
refs: batch, row, record SHA, относительный raw key, occurred/observed. Новая копия
уже видимого event не становится новым событием. У одного нового event может
быть несколько receipts, поэтому event_count и receipt_count различаются.
В `run evidence` я показываю `visible_in_run` у каждого receipt; вход в provenance
сам по себе не означает участие в сумме.

Если engine SHA отличается, `engine_changed=true`. Если изменился временной
контракт, отдельно возвращаю visibility_changed. Я не называю все отличия
исключительно следствием late data: версия расчёта тоже может быть причиной.
Сравнение не является автоматическим доказательством причинности или сверкой
правильности двух движков. Сами результаты я пока не запускал.

## Почему я не продвигаю Case корректировкой

В CG-203 текущая карточка относится к монотонному потоку as-was магазина. Новый
отчёт о вчерашнем состоянии не должен откатить сегодняшнюю карточку. Я сохраняю
этот контракт и возвращаю CASE_CORRECTION_REPORT_ONLY при попытке применить
as-known-now. Для актуального наблюдения могу подготовить обычный as-was с более
новым business cutoff, включающий поздние данные по своим границам. Перенос
результата исторической корректировки в актуальный workflow требует отдельной
политики; я фиксирую его как дальнейшее развитие, не обхожу guard и не притворяюсь,
что написал ручное закрытие или автоматическую бухгалтерскую корректировку.

## Маршрут знакомства, который я пока не выполнял

Я сначала читаю WORKBENCH и RESULTS, принимаю только синтетические OMS/PSP, затем
выбираю T0 после фактической публикации обычных пакетов. Нельзя взять произвольную
прошлую дату до их приёма и ожидать, что as-was увидит ещё не опубликованные входы.
T1 выбираю после приёма late пакета, но не в будущем относительно часов БД.
В командах заменяю T0/T1 на реальные RFC3339, R1/R2 на выданные UUID.

```text
python -m commerceguard run prepare --merchant demo_shop --as-of T0 --reason manual
python -m commerceguard run execute --run-id R1
python -m commerceguard run prepare --merchant demo_shop --as-of T0 --mode as-known-now --knowledge-at T1 --baseline-run-id R1 --reason late-data
python -m commerceguard run execute --run-id R2
python -m commerceguard run changes --run-id R2 --limit 20
python -m commerceguard run evidence --run-id R2 --order-id O-102 --limit 20
```

Я не обещаю, что фиксированные времена старого генератора дадут ровно этот пример
observed-late при запуске в любой день: technical publication lateness и source
observed lateness различаю. Для сценария выше мне нужны согласованные синтетические
времена, суммы и заново рассчитанные файловые manifests.

Ошибочный baseline, отсутствующий result, будущее knowledge и нарушение порядка
времён дают отказ до публикации плана. Неизвестный исход COMMIT восстанавливаю
повтором того же запроса и чтением сохранённого run ID; старые results не удаляю.
Я не выполнял конкуренцию, временные граничные случаи, SQL или эти команды.

## Пять упражнений с ориентиром ответа

1. Я задаю occurred=T0−1, observed=T0+1 и knowledge=T0. Ожидаю невидимость.
   При knowledge=T0+2 ожидаю видимость; исходные timestamps остаются прежними.
2. Я ставлю occurred=T0+1 и knowledge=T0+2. Ожидаю невидимость: business cutoff
   не передвинулся. Проверку ответа нахожу в двух условиях фильтра reconcile.
3. Я сравниваю R2 с baseline другого merchant или с другим as_of. Ожидаю отказ,
   потому что это уже сравнение разных бизнес-состояний, а не корректировка знания.
4. Я добавляю receipt уже видимого event. Ожидаю новый input/receipt provenance,
   но не newly_visible_event. Проверку ответа нахожу в NOT EXISTS baseline evidence.
5. Я вызываю case apply R2 для as-known-now. Ожидаю REPORT_ONLY и сохранение head.
   Затем проектирую отдельную политику promotion: явно отвечаю, какую дату и какое
   человеческое решение она вправе менять, прежде чем добавлять код.

На собеседовании я могу объяснить event time/knowledge time/publication marker,
replay immutable manifest, reason lineage, разницу event и receipt, ограничения
MVCC-реконструкции и причины, по которым historic correction не равна current Case.
