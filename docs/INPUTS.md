# CG-102: manifest, CSV и JSONL

24.10.2026, 0.1.0.dev2. Формат и parser написаны **без исполнения**. Все примеры
ниже — спецификация, не stdout выполненной команды. Загрузки в БД пока нет.

## Один пакет — один магазин и источник

Пользователь явно передаёт два пути: JSON manifest и файл данных. Manifest **не**
содержит пути, имени файла или URL. Его source выбирает формат: oms → CSV,
psp → JSONL. Расширению файла parser не доверяет и сам не ищет файлы по директориям.
Обычные файлы, UTF-8, необязательный единственный BOM в самом начале, LF/CRLF.
Код не читает Excel, ZIP, URL, pipe и файлы через конечную symlink.

| Поле manifest | Тип/ограничение | Назначение |
| --- | --- | --- |
| contract_version | int ровно 1, не bool | Версия envelope и формата строк |
| source | oms либо psp | Один источник и один формат на пакет |
| merchant_id | ID из предметного контракта | Каждая строка должна иметь тот же магазин |
| content_sha256 | 64 lowercase hex | Hash всех исходных байтов файла данных |
| row_count | int 0..1000000 | Все записи данных, включая точные PSP-повторы; CSV header не входит |
| byte_count | int 0..100000000 | Все байты, включая BOM, кавычки и окончания строк |
| observed_at | RFC3339 с известным offset | Объявленный момент знания пакета |
| effective_at | Только OMS, RFC3339, <= observed_at | Момент действия полного снимка |
| is_complete | Только OMS, ровно true | Утверждение источника, что снимок полный |

Никаких дополнительных/неизвестных полей. PSP envelope не содержит effective_at
или is_complete. Manifest ограничен 64000 байт. bool не заменяет row_count=1.
Размеры — десятичные байты, не MiB. Максимальный raw record — 1000000 байт UTF-8,
включая окончания его строк. Более ранний предел отдельного поля csv-движка тоже
может отказать; глобальный csv.field_size_limit наш код не изменяет.

Время: YYYY-MM-DDTHH:MM:SS с необязательной дробью до 6 знаков, затем Z либо
±HH:MM. Пробел вместо T, naive datetime, leap second и неизвестное смещение
-00:00 не допускаются. Календарную корректность проверяет datetime, нормализация
идёт в UTC. Значения observed_at в учебных historical inputs объявляет источник;
parser не подтверждает их достоверность криптографически и не читает системные часы.
Приём в БД должен отдельно сохранять техническое время получения и политику доверия.

## OMS CSV

Точный заголовок, порядок, разделитель-запятая, doublequote и кавычка `"`:

```csv
merchant_id,order_id,currency,capture_due_minor,refund_due_minor,settle_after
M01,O1002,RUB,12000,0,2026-10-23T12:00:00Z
```

У примера одна запись данных. Quotes допустимы по CSV, но смысл значений строгий:
никаких пробелов вокруг ID, денег в рублях с точкой, знака плюс, экспоненты или
ведущих нулей, кроме самого 0. Суммы — minor int, границы из domain.py. Неверное
число колонок — CSV_WIDTH; повтор ключа merchant/order в одном полном снимке —
OMS_DUPLICATE, даже для равных строк. is_complete=false — отказ до чтения записей.
Пустой OMS-снимок содержит header и row_count=0; файл без header недопустим.

CSV reader получает поток с newline='', поэтому умеет отличать физические строки
от логической записи. Даже если кавычка захватывает несколько строк, общий raw
record ограничен. Перенос внутри ID/даты не становится допустимым значением:
предметный контракт всё равно его отклонит. Header имеет diagnostic record=0.

## PSP JSONL

Каждая физическая строка — один JSON object с ровно восемью полями:

```json
{"merchant_id":"M01","source_event_id":"C02","order_id":"O1002","currency":"RUB","kind":"capture","amount_minor":11000,"occurred_at":"2026-10-22T10:00:00Z","observed_at":"2026-10-22T10:01:00Z"}
```

kind capture/refund, amount_minor — положительный int, не bool/float/string.
JSON decoder отклоняет повторяющийся ключ на любой вложенности, NaN/Infinity,
дроби и слишком длинные числовые литералы. Неизвестные поля не пропускаются.
Пустые/пробельные строки запрещены; финальный newline допустим и не добавляет
пустую запись. Пустой PSP-файл допустим при byte_count=0 и row_count=0.
Массив вместо object недопустим, как и несколько объектов на одной строке.

occurred_at <= observed_at строки <= observed_at пакета. Магазин строки совпадает
с envelope. Один merchant/source_event_id и равный смысл — точный повтор;
он остаётся raw record и входит в row_count, но увеличивает duplicate_rows,
не unique_keys. Разный смысл под тем же ID — PSP_CONFLICT всего пакета.
Равные повторы могут иметь разные observed_at: оно не часть fingerprint.

Политика выбора earliest observed_at до нормализации и обработка исторического
факта относительно уже опубликованной неизменяемой записи относятся к CG-103.
Этот parser обнаруживает только повторы/конфликты **внутри одного пакета**, не в БД.

## Три разных SHA-256

1. content_sha256 — все исходные байты файла. BOM/CRLF/пробелы меняют этот hash.
   Он идентифицирует артефакт, но не доказывает подлинность отправителя.
2. record_sha256 — UTF-8 decoded raw_text логической записи с её окончаниями строк.
   Начальный BOM декодер снимает, header не становится InputRecord. Первичные байты
   всегда представлены hash всего файла; hash записи не выдаётся за hash byte slice.
3. semantic_sha256 — нормализованный смысл. Quotes, JSON key order, пробелы,
   эквивалентные timezone offset и запись доли секунды его не меняют.

PSP canonical JSON array перед SHA:

```text
["psp:v1", order_id, currency, kind, amount_minor, occurred_at_utc]
```

merchant/source_event_id остаются отдельным business key; observed_at не входит.
OMS array:

```text
["oms:v1", merchant_id, order_id, currency, capture_due_minor,
 refund_due_minor, settle_after_utc]
```

JSON separators=(',', ':'), ensure_ascii=true, UTF-8/ASCII bytes. UTC-время имеет
ровно шесть знаков долей и Z, например 2026-10-22T10:00:00.000000Z.
Изменение этого определения требует версии hash-контракта; нельзя незаметно
обновить writer и назвать старые записи конфликтными.

## Как устроено чтение

file_contracts.py отвечает за envelope, типы, даты и semantic hash. file_inputs.py
открывает только явно заданные файлы и сначала копирует данные блоками по 64000 байт
в TemporaryFile, одновременно считая hash и размер. При расхождении разбор не
начинается. Затем parser читает именно эту копию, поэтому не хэширует одну версию
входа и не разбирает другую после внешнего изменения файла.

TemporaryFile закрывается контекстом; постоянный raw repository ещё не пишется.
Временная копия потребляет до byte_count диска. В памяти текущая запись и словарь
hash по уникальным ключам: память O(unique keys), не O(1). Максимальная память и
скорость не измерялись. Ограничение 10^6 записей — договор контракта, не benchmark.

open_input(manifest_path, data_path) выдаёт PreparedInput. records() — однопроходный
итератор InputRecord: ordinal, физический диапазон строк, raw_text, два hash и
типизированный OrderExpectation/PaymentEvent. raw_text нужен будущему ingest,
но CLI его не печатает. summary() доступен только после полного EOF и совпадения
row_count. Нормальный выход из контекста с недочитанным потоком тоже считается
STREAM_INCOMPLETE: будущий caller не должен принять prefix за завершённый batch.

## Команда для самостоятельного использования

Я пока не выполнял эту команду. В корне checkout с Python своей .venv:

```bash
.venv/bin/python -m commerceguard input inspect --manifest workspace/input/oms.manifest.json --data workspace/input/orders.csv
```

В Windows путь Python — .venv/Scripts/python.exe. Оба файла пользователь готовит
сам; приведённые пути — пример. SHA/byte_count вычисляются по фактическим байтам,
не копируются из документа. Генерация набора демонстрационных файлов остаётся
историей CG-105, не выдана за готовую сейчас. Сторонние пакеты/Psycopg для inspect
не нужны. Нет сетевых обращений, записи в БД или публикации данных.

При успехе печатаются только source, merchant, version, counts, checksum и время
пакета. Это метаданные результата разбора, не «published». При ошибке код процесса 2,
фиксированный error code, номер записи и при необходимости известное имя поля.
Не печатаются payload, неизвестные JSON keys, имена файлов и полный exception I/O.
Необработанная ошибка исполнения всё ещё возможна: код не запускался.
