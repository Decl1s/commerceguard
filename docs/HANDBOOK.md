# Как я меняю и сопровождаю CommerceGuard

## Моя граница первой версии

Я поставляю один экземпляр для одной организации, несколько merchant с явным
разграничением доступа и файловым обменом OMS/PSP. Я выбрал PostgreSQL как источник
истины, поскольку финансовый факт, результат и человеческое решение нуждаются
в транзакциях, ограничениях и воспроизводимости. Prefect управляет последовательностью
задач, dbt строит аналитические представления, Waitress обслуживает рабочее место.
Эти инструменты не заменяют друг друга. Платного облака и постоянного Prefect server
для первой версии мне не требуется.

Я поддерживаю проверенный профиль Linux x86_64, Docker Compose, локальный доступ.
Для внешней команды отдельно настраиваю DNS/TLS и защищённый хост по DEPLOYMENT.
Я не называю входящий файл банковской транзакцией, а закрытие карточки — возвратом
денег. Приложение объясняет расхождения и сохраняет решения; платежей оно не делает.

## Где я меняю поведение

| Задача | Место | Почему я выбрал эту границу |
| --- | --- | --- |
| Новый внешний PSP формат | Отдельный adapter перед file_contracts/file_inputs | Я нормализую внешний контракт, не добавляю особенности поставщика в денежную формулу |
| Новая формула | domain/reconcile, затем engine identity/run contract | Я сохраняю объяснимость и возможность прочитать прежний результат |
| Новое поле хранения | Новая migration0016 и соответствующий store | Я не переписываю опубликованную историю0001…0015 |
| Новый показатель | analytics/models и schema.yml, затем catalog | Я задаю grain/key/time/currency до JOIN и не размножаю суммы |
| Новый переход карточки | case_workflow и SQL guard | Я проверяю роль, scope, версии, request и аудит в одном COMMIT |
| Новый фильтр/оформление | workbench_store/workbench | Я меняю чтение и представление, не canonical financial facts |
| Новый повтор фоновой задачи | pipeline или backfill | Я повторяю по сохранённым identities, не выбираю незаметно новые входы |

Я начинаю изменение с контракта и примера: какие bytes считаются тем же событием,
какая временная граница действует, что происходит при повторе и кому доступно
действие. Затем связываю файл с одной историей в Kanban, выполняю проверки нужного
слоя и записываю факт в WORKLOG. Так таблица отражает поставку, а не обещания.

## Как я принимаю реальные файлы

Я готовлю manifest по INPUTS и явно выбираю два файла. Я не сканирую домашнюю
папку, не монтирую её в tools и не помещаю DSN в аргументы. Из корня checkout:

```bash
python3 deploy/import_input.py --manifest workspace/input/oms.manifest.json --data workspace/input/oms.csv
python3 deploy/import_input.py --manifest workspace/input/psp.manifest.json --data workspace/input/psp.jsonl
```

`import_input.py` передаёт только выбранные bytes в stdin временного tools
контейнера. Два размера ограничены64000/100000000 байт, version prefix обязателен,
обрезанный поток и лишние bytes отвергаю. Имена в контейнере фиксированы, путей
из архива и extractall нет. Scratch удаляю после вызова, raw храню по hash.
Полную проверку manifest/hash/rows выполняет существующий publish_input; транспорт
её не обходит. Повтор тех же bytes создаёт duplicate_batch, не новые деньги.

Приём пакета не запускает автоматически сверку и не продвигает очередь. После
приёма обоих файлов я явно создаю run, записываю напечатанный run_id, выполняю и
применяю его. Значение AS_OF заменяю на нужную RFC3339 UTC границу:

```bash
docker compose --env-file workspace/deployment/.env -f deploy/compose.yml run --rm tools cli run prepare --merchant M01 --as-of AS_OF
docker compose --env-file workspace/deployment/.env -f deploy/compose.yml run --rm tools cli run execute --run-id RUN_ID
docker compose --env-file workspace/deployment/.env -f deploy/compose.yml run --rm tools cli case apply --run-id RUN_ID
```

Это сознательная граница: успешная загрузка ещё не подтверждает полноту суток,
а сохранённый исторический correction не должен сам менять рабочий baseline.
Для полного preflight/ingest/dbt использую pipeline из ORCHESTRATION; для периода —
BACKFILL. Автоматическое расписание и прямые PSP API оставляю за объёмом версии1.

## Как я провожу обновление

Я записываю текущий tag, schema version, последний canonical run и результат
readiness. Затем останавливаю web/proxy и инженерные jobs, создаю согласованный
DB+raw backup owner tools и выполняю verify. Копию переношу на отдельное закрытое
хранилище: volume на том же диске не защищает от потери диска. Я пробую восстановить
её в отдельный пустой экземпляр по BACKUP, прежде чем рассчитывать на копию.

Я сохраняю checkout старого tag и настройки отдельно от нового checkout; секреты
не генерирую заново. Для Compose сохраняю project name commerceguard: иначе Docker
создаст другие volumes и пустая база будет похожа на потерю данных. Новый образ
собираю из зафиксированного tag. Init применяет только новые миграции и runtime
grants; существующий пароль первого аккаунта не меняет. Я проверяю readiness,
вход, очередь, конкретный старый run/result SHA и пробный экспорт.

Я не делаю downgrade SQL поверх новой схемы. Если обновление не подходит, останавливаю
новые процессы и восстанавливаю проверенную пару DB+raw в отдельную пустую БД
с прежним tag. Период после backup потребует явного повторного приёма пакетов.
Restore отзывает sessions: вхожу заново. При прерывании после DB COMMIT читаю receipt
и выполняю finish_restore, а не второй pg_restore поверх непустой базы.

## Как я разбираю сбои

Я начинаю с `/livez`, `/readyz`, состояния Compose и ограниченных JSON событий.
В логах нет паролей, Cookie, URL query, комментариев и raw rows.401 означает
вход/expiry/active,403 — роль/scope/CSRF/Origin,409 — конфликт актуальных версий.
После503 сохраняю прежний request_id и тело, поскольку COMMIT мог уже произойти.
Повтор ровно той же команды читает прежний audit; изменённое тело получает409.
Новые UUID на каждый сетевой retry превратили бы неопределённость в двойное действие.

При stale source я проверяю отдельно последнюю попытку, последнюю публикацию,
observed watermark и business completeness. Empty PSP не доказывает нулевые деньги;
объявленная граница источника не становится поздним событием. При конфликте PSP
я не UPDATE канонический факт: исправляю внешний контракт/новую допустимую ревизию.
При dbt failure старый immutable report уже может существовать; resume продолжает
по его ID и не выдаёт сбой витрин за полный успех.

Я контролирую свободное место, рост raw/attempts/audit, возраст backup, успешность
восстановления и время ответа очереди. Автоматической retention нет: бессрочное
накопление нужно планировать, а удаление raw разрушило бы доказательства. EXPLAIN
на2000Case и40HTTP запросов с4 клиентами — проверка выбранного сценария, не capacity
plan для тысяч пользователей. Перед увеличением объёма я измеряю репрезентативные
данные, диски и реальные границы, не обещаю произвольный SLA.

## Мои задания с проверкой ответа

1. Я импортирую один синтетический PSP дважды. Проверка: второй ответ содержит
   duplicate_batch=true, количество canonical facts не растёт. Затем меняю data
   без пересчёта manifest SHA: весь пакет должен быть отклонён.
2. Я добавляю currency в собственную витрину. Проверка: ключ содержит currency,
   RUB и USD не попадают в одну сумму; каталог описывает grain и NULL semantics.
3. Я открываю карточку в двух вкладках и назначаю исполнителя. Проверка: старая
   форма получает409, а в human audit ровно одно успешное действие.
4. Я создаю отдельный backup, меняю байт raw только в копии и запускаю verify.
   Проверка: SHA mismatch, restore не запускаю. Рабочую raw копию не трогаю.
5. Я меняю только CSS и запускаю unit/browser smoke. Проверка: UI меняется,
   engine SHA и финансовые результаты остаются прежними. Если меняю формулу,
   создаю новую identity и не требую старый execute выполнить другим движком.

На собеседовании я объясняю, почему raw first допускает orphan, почему uncertain
COMMIT не означает rollback, почему latest отличается от canonical, зачем два
времени и почему human workflow отделён от presence. Я показываю конкретные
исходники и фактически выполненные проверки, сохраняя учебное происхождение проекта.

[PostgreSQL backup](https://www.postgresql.org/docs/16/backup.html),
[transaction isolation](https://www.postgresql.org/docs/16/transaction-iso.html).
