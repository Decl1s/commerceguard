# Я связываю показатель с его контрактом

Я храню машинно проверяемый каталог в `commerceguard/catalog.json`, рядом с кодом,
а не в отдельном внешнем сервисе. Для девяти локальных dbt views отдельный сервер
каталога добавил бы сопровождение без нового полезного поведения. JSON читается
стандартной библиотекой, review проходит вместе с SQL, подключение к БД не нужно.

```bash
.venv/bin/python -m commerceguard.catalog list
.venv/bin/python -m commerceguard.catalog show mart_reconciliation_currency
.venv/bin/python -m commerceguard.catalog check
```

`list` даёт маршрут по моделям, `show NAME` — полный контракт выбранного показателя,
`check` проверяет весь каталог и код SQL. Неизвестное имя завершает команду кодом2;
я не подменяю отсутствие произвольной моделью. Каталог не меняет данные и витрины.

| Поле | Для чего я его храню |
| --- | --- |
| `grain`, `key` | Я обозначаю одну строку и состав identity до построения JOIN |
| `currency_scope`, `currency_policy` | Я запрещаю читателю выводить общий денежный итог по RUB/USD/EUR |
| `time_policy` | Я связываю показатель с as_of/knowledge_at сохранённого run либо cutoff settlement |
| `lineage`, `path` | Я показываю точный SQL и его ref/source родителей |
| `meaning_owner` | Я называю роль, которая согласует смысл; реального владельца/клиента не выдумываю |
| `metrics`, `limitations` | Я фиксирую формулу ключевых полей и границы интерпретации |

Я покрываю все SQL-модели, включая staging и intermediate, хотя конечных marts три.
Валидация сравнивает множество путей с `analytics/models/**/*.sql`: новая SQL-модель
без записи каталога сразу нарушит проверку. Для каждой записи я требую непустые
ключи, времена, валютную политику, роль, метрики и ограничения. Связи `ref/source`
сверяю с настоящим SQL и проверяю граф на циклы. Парсер намеренно поддерживает
нынешний стиль dbt вызовов с literal single-quoted именами: динамический Jinja
потребует перехода на dbt manifest, а не обещания универсального SQL parser.

Я не называю эту структурную проверку доказательством бизнес-формулы. Если заменить
SUM на AVG и сохранить имена зависимостей, каталог останется структурно корректным.
Корректность денег по-прежнему проверяю отдельными SQL/data tests и kernel tests.
Словарь ключевых метрик не является исчерпывающим словарём каждой технической
колонки; полный контекст полей остаётся в MARTS, SETTLEMENT и SQL.

Например, `mart_reconciliation_currency` имеет зерно run/merchant/currency. Один
заказ может дать несколько findings, поэтому `finding_count` не число заказов.
`known_actual_capture_minor` — сумма известных фактов. При `blocked_orders>0` она
частичная; NULL не превращаю в ноль. Finding-only USD даёт строку даже без OMS
balance, поскольку FULL JOIN сохраняет её. Я не складываю эту строку с RUB и не
выбираю latest run автоматически.

Для settlement я читаю `report_id`, а не business settlement_id как identity
строки: разные advice revisions/cutoffs/tariffs могут описывать один пакет. Если
сложить их без выбора конкретного отчёта, получится повторный учёт. Fee я считаю
один раз на gross и не распределяю произвольно по заказам. Unknown expected net
остаётся NULL, полный пустой advice даёт известные нули.

## Как я меняю проект

1. Я меняю SQL и явно формулирую новое зерно, особенно до JOIN нескольких событий.
2. Я обновляю запись JSON, ключевые формулы и ограничения.
3. Я запускаю `catalog check` и подходящие dbt tests на синтетических данных.
4. Я документирую изменение смысла в ADR, если меняется контракт потребителя.

## Что я могу потрогать

- Я удаляю запись `int_refund_by_order` в локальной копии. Ожидаю CATALOG_COVERAGE;
  после возврата записи check снова успешен.
- Я меняю lineage валютной витрины на выдуманный source. Ожидаю CATALOG_LINEAGE,
  а не тихо красивый, но ложный граф.
- Я добавляю SQL модель без каталога. Ожидаю отказ покрытия, затем дополняю контракт.
- Я объясняю, почему SUM по всем report_id не даёт выручку магазина. Ответ: повторные
  расчёты и ревизии одного бизнес-пакета плюс независимые валюты.
- Я делаю CSV словарь из `metrics` отдельной read-only командой. Проверяю отсутствие
  подключения к БД и сохранение русских пояснений; это упражнение, не готовая функция.
