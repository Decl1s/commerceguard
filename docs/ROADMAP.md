## Состав демонстрации каждого этапа

S1: повтор одного файла даёт тот же batch; конфликт source_event_id описывается
явной причиной, half-loaded snapshot не публикуется. Пользователь видит ID пакета,
счётчики и свежесть, а не только «успех» команды.

S2: сверка из PRD, сохранённые входные ссылки, повтор того же ключа запуска,
поздний C02L в новом run; карточка и прежнее объяснение не исчезают.

S3: граф шагов, параметры периода, витрина по валюте, отдельный settlement-level
расчёт комиссии, путь показателя через ref к исходным facts.

S4: короткая работа финансового специалиста — фильтр → evidence → назначение →
решение. Два изменения одной версии карточки приводят к явному конфликту.

S5: сценарии из RUNBOOK с описанием каждого ожидаемого состояния после сбоя;
восстановление raw manifest, retry загрузки и backfill без перезаписи старого run.

S6: 10-минутный narrative, диаграммы, скриншоты только реально существующих экранов,
таблица возможностей, границы модели, объяснение решений для собеседования.

## Первоначальный переход без исполнения

Оставляем запись фактического состояния, известных ограничений и следующей истории.
Запрет исполнения не обходим: сценарии остаются спецификацией/исходниками,
готовность не подтверждается. Если объём не помещается, переносим целую историю,
сохраняя одну цель спринта. Готовые планы S3–S6 уточняются только при приближении,
не превращаются сейчас в тысячи строк неподключённого кода.
