# Как я пересчитываю период

Я разделил plan/start/resume. `python -m commerceguard.backfill plan --merchant M01
--start 2026-10-01 --end 2026-10-03 --timezone Europe/Moscow` печатает JSON без
подключения к БД и без расчёта. Сохраняю его в своей workspace, затем явно вызываю
`backfill start --plan workspace/plan.json` и `backfill resume --job-id HASH`.
Параметр `--dsn-env` относится к модулю и указывается перед подкомандой.

План содержит1…31календарных дней, pinned timezone, balance-v2 и точный engine SHA.
Cutoff каждого дня — перед следующей местной полуночью. При DST день может иметь
23/25часов; отсутствующий календарный день отвергаю. `--through RFC3339` явно
обозначает частичный последний день, в том числе сегодняшний; будущее исполнение
запрещаю. Полный текущий день ещё не закончился, его нельзя молча считать закрытым.

As-was сохраняет историческую видимость: файл, принятый сегодня, не существовал
вчера для published marker. Я не подделываю задним числом загрузку ради backfill.
As-known-now требует `--knowledge-at` и `--baselines FILE` с отображением каждой
даты на точный опубликованный baseline run_id того же cutoff. Нет baseline —
нет выдуманной correction. Ruleset другой версии требует соответствующего кода.

Start закрепляет immutable run manifests всех дней и сохраняет их в schema13.
Exact start возвращает прежний job. Если процесс прервётся до сохранения job,
могут остаться prepared manifests, но не ложный успешный результат. Resume работает
только с сохранёнными run IDs, максимум31день за вызов, останавливается на первом
отказе и сохраняет безопасный код. После crash между result COMMIT и job update
exact execute вернёт тот же результат. После100неуспешных ручных попыток нужен
разбор, бесконечный retry не создаю. Другой engine требует прежних байтов, а не
перезаписи старого плана. Session advisory lock исключает двух исполнителей job.

Я не продвигаю исторический backfill в текущую Case очередь и не меняю финансовый
baseline. Dbт views читают сохранённые результаты после обычного rebuild. В проверке
я создал реальный частичный план, внедрил остановку execute, возобновил прежний
run ID и подтвердил повтор завершённого job без новых действий. Упражнение: вызвать
resume дважды, сравнить IDs/SHA и объяснить разницу между новым планом с другим
cutoff и retry прежнего job.
