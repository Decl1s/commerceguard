## Срез CG-101

Написаны bootstrap.sql, 0001_storage_foundation.sql, migrations.py и команды
db status/migrate. PostgreSQL 16, отдельная БД commerceguard, одна одноимённая схема.
Драйвер загружается только для db; demo сохраняет stdlib-сценарий без БД.
Зафиксированы версии драйвера и Python-транзитивных зависимостей из PyPI.
Установка не выполнялась. Подробности: [STORAGE](../STORAGE.md), ADR-13/14.

Критерии в исходниках: отказ при чужой БД/схеме/формате/истории, непрерывные версии,
hash SQL, fail-fast advisory lock, одна транзакция для bootstrap и всех pending
миграций, нет DROP/reset, текст драйвера с параметрами не выводится.
Ни один критерий не проверялся исполнением. Функции и ограничения SQL — написанное
намерение, не подтверждённое поведение сервера.

## Срез CG-103

Версия 0.1.0.dev3. Написаны raw_store.py, postgres.py, ingestion.py, stage_input.sql
и миграция 0002, не изменяющая 0001. Canonical manifest SHA — identity batch;
raw data SHA — identity точных байтов. PostgreSQL хранит envelope, относительные
ключи и счётчики. Одна транзакция охватывает COPY, полный EOF, повторы/конфликты,
весь raw, snapshot/новые события/receipts и published. Точный replay не вставляет
строки; earlier observed_at существующего PSP вызывает TEMPORAL_CONFLICT.

Минимальная команда ingest publish связывает срез; полный status и генератор
остаются CG-105. Состояния received/staged не видны между транзакциями. Ошибки
пока не создают persistent failed/quarantined batch; orphan raw остаётся на диске.
Сбой COMMIT может иметь неизвестный исход, повторяется тот же manifest.
Карантин/recovery — следующий CG-104. Подробности: [INGESTION](../INGESTION.md).
Ни filesystem-протокол, ни SQL, COPY, locks, CLI или rollback не исполнялись.

## Срез CG-104

Я добавил миграцию 0003 и ingest_attempt, не меняя 0001/0002. Регистрацию started
фиксирую до COPY; success/duplicate — вместе с core. Отказ записываю отдельно,
только если attempt ещё started. Терминальную историю не изменяю. Структурный или
бизнес-отказ карантинит весь пакет, сохраняя raw evidence без частичного core.
Scan-raw показывает ограниченный read-only обзор, recover перепроверяет объект
по canonical manifest hash и повторяет обычный publish. Недоступный журнал явно
отражаю в CLI. Код и SQL не запускал. Дальше — CG-105, status и генератор.

## Срез CG-105 и обзор написанного S1

Я добавил sample_data.py и ingest_status.py, CLI input generate/ingest status.
Воспроизводимые примеры: 5 OMS-строк, 7 PSP-строк с дублем, позднее событие отдельно;
варианты invalid-json/conflict/earlier-observed. Status читает metadata по одному
из batch/attempt/manifest ID, ограничивает историю и не печатает raw payload.
Существующий output-каталог не заменяю. Подробный маршрут и ручные ориентиры —
WORKBENCH. Версия dev5, новых зависимостей и миграций нет.

Все пять историй S1 написаны и переданы в Review, но цель корректного работающего
ingestion не подтверждена: я не запускал ни один сценарий. Следующим беру CG-201
в S2, опираясь на написанный контракт без заявления о приёмке S1. Практическое
улучшение: у входного, пакетного и attempt уровня разные ID и разные команды;
их нельзя смешивать с будущим run ID. Открытые риски: отсутствие исполнения,
raw orphan/power loss, unavailable journal, legacy migration и исторические коррекции.
