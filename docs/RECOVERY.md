# CG-104: карантин и восстановление приёма

24.10.2026. Я написал этот срез без исполнения приложения, SQL и проверок.
Обозначаю исходники unverified. Ни один описанный ниже исход не выдаю за результат запуска.

## Почему попытка не равна пакету

В CG-103 я объединил batch, raw-строки, snapshot/события и published одним COMMIT.
Это защищает видимость полного снимка, но после rollback исчезает и диагноз.
В CG-104 я добавил ingest_attempt. У одной identity пакета может быть много попыток;
у каждой свой UUIDv4. Бизнес-пакет сохраняет прежний UUIDv5 canonical manifest.
Retry создаёт новую попытку, но не новый платёж и не новый OMS-снимок.

Я не создаю ingest_batch со статусом quarantined из частично разобранных строк.
Карантин здесь — терминальное состояние попытки целого пакета. В core не попадает
даже валидный prefix файла. Старую ingest_quarantine с FK на raw record я пока
не использую: при ошибке parser полного набора DB raw-строк ещё нет. Вместо фиктивной
строки в этой таблице сохраняю manifest hash, raw key, ordinal и безопасный код в attempt.

## Три транзакционные границы

1. Фиксирую вход, сохраняю raw и canonical manifest, как в CG-103.
2. Отдельной короткой транзакцией регистрирую started attempt. Только после её
   подтверждения начинаю COPY. Если она не подтверждена, не заявляю наличие журнала.
3. Публикую весь пакет следующей транзакцией. В её конце меняю attempt на published
   или duplicate. Успешная попытка и её published batch фиксируются одним COMMIT.
4. После ошибки пробую отдельное соединение для записи диагноза. Оно обновляет
   только started. Уже терминальное состояние не затираю новым сообщением об ошибке.

Если сеть пропала после COMMIT, сервер мог успеть сохранить и batch, и успешную
попытку. Поэтому UPDATE rejection имеет WHERE state='started'. Блокировка строки
и терминальный trigger не дают перезаписать published состоянием unknown.
Если журнал недоступен, ошибка CLI содержит journal=unavailable. Я не печатаю
«карантин сохранён», когда отдельный COMMIT не подтверждён.

## Состояния и безопасный диагноз

| Состояние | Как я его использую |
| --- | --- |
| started | Попытка зарегистрирована; исход ещё не зафиксирован |
| published | Этот вызов опубликовал пакет |
| duplicate | Этот вызов полностью прочитал точный replay без новых фактов |
| quarantined | Структурная или бизнес-ошибка отвергла весь пакет |
| failed | Известное препятствие, например MERCHANT_BUSY или недоступный raw |
| unknown | Нет подтверждения исхода БД, неожиданная ошибка или прерывание |

Структурные ошибки: UTF-8, CSV/JSON, набор полей, типы, row count. Бизнес-ошибки:
OMS_DUPLICATE, PSP_CONFLICT, TEMPORAL_CONFLICT и BATCH_CONFLICT. Инфраструктурные:
файлы, схема, занятый lock и неподтверждённая БД. Для DatabaseError я консервативно
выбираю unknown; один факт исключения не доказывает rollback.

В журнал не пишу str(error), строку PSP, DSN, абсолютный путь, сумму или ID события.
Разрешаю только фиксированный code, категорию, ordinal и имя из известного набора
полей контракта. Неизвестные JSON-ключи не становятся диагностическим payload.
CLI сообщает attempt_id и journal=recorded/already_terminal/not_registered/unavailable.
При KeyboardInterrupt пробую записать unknown/interrupted; авария питания или kill
могут оставить started. Exit code прерывания — 130, остальных отказов — 2.

Если manifest невалиден или исходный файл не совпал с его SHA/размером, подтверждённой
identity пакета ещё нет. Такая preflight-ошибка может остаться без DB attempt;
CLI явно показывает not_registered либо unavailable. Не сохраняю произвольные
ошибочные байты под именем hash, заявленного источником. Это граница текущего журнала.

## Как я нахожу orphan

RawStore.discover читает только собственный root с корректным маркером и фиксированные
256 shard-каталогов manifests. Рекурсивный обход компьютера и имена из manifest
не использую. Известные имена имеют вид SHA.json и совпадают с префиксом shard.
Ссылки и посторонние записи пропускаю счётчиком без публикации их имён.

Обзор ограничен --limit от 1 до 1000, по умолчанию 100; truncated сообщает, что список
неполный. Внутри shard порядок задаёт filesystem, поэтому этот интерфейс не является
полной пагинацией. Для конкретного объекта использую явный manifest SHA.
В обзорном режиме проверяю canonical manifest, его hash, тип и размер data object.
Полный data hash не читаю: иначе 100 объектов могли бы потребовать чтения 10 GB.
В каждой записи явно стоит data_hash=not_checked. Перед recovery читаю и сверяю все байты.

Одним коротким READ ONLY/REPEATABLE READ снимком сопоставляю manifest hashes с БД.
Сначала учитываю published batch, затем последнюю попытку. Статусы:
published, blocked, quarantined, failed, unknown, orphan, damaged.
started или неизвестный исход не объявляю orphan. Даже orphan — наблюдение на момент
обзора: параллельный загрузчик мог уже сохранять файл до регистрации своей попытки.
Сканирование ничего не удаляет и не запускает автоматически.

## Как я восстанавливаю

Для recover нужен только SHA canonical manifest и явно выбранный raw root.
Перепроверяю маркер, собственные каталоги, отсутствие конечных symlink, manifest
контракт/канонизацию/hash, размер и SHA данных. Затем вызываю тот же publish_input:
новый attempt, полный parser/COPY до EOF, те же locks и semantic/temporal правила.
Прямой INSERT в core, пропуск валидации, force и обновление старых фактов не добавляю.

Если первый COMMIT состоялся, recovery завершится duplicate. Если пакет не был
опубликован, он может опубликоваться целиком. Если исходный файл содержит бизнес-
конфликт, он снова отклонится: recovery не исправляет содержание. Для исправленного
файла нужен новый правдивый manifest. Исторические attempts остаются в журнале;
новый успех не переписывает прежний quarantine/unknown.

Объект без canonical manifest нельзя восстановить только по data hash: у одинакового
OMS CSV бывают разные effective snapshots. Нужен исходный envelope. Не угадываю время
источника и не удаляю «бесхозный» data object. .pending cleanup, retention, journal
выгрузка при недоступной БД и disaster recovery относятся к дальнейшей эксплуатации.

## Карта кода и подготовленные команды

| Файл | Моё решение |
| --- | --- |
| sql/migrations/0003_ingest_attempts.sql | Отдельная история попыток, ограничения и один переход started → terminal |
| ingest_journal.py | Регистрация, success в core transaction, безопасная классификация и best-effort failure COMMIT |
| ingestion.py | Новый attempt_id на вызов и прежняя identity пакета; ошибки без server DETAIL |
| raw_store.py | Чтение собственных объектов, ограниченный discovery и полная сверка перед recovery |
| recovery.py | Обзор статусов и повтор полного пути вместо обхода контракта |

После самостоятельной подготовки окружения и явного db migrate команды из корня:

```bash
.venv/bin/python -m commerceguard ingest scan-raw --raw-root workspace/raw --limit 100
.venv/bin/python -m commerceguard ingest recover --raw-root workspace/raw --manifest-sha SHA256
```

SHA256 заменяю на 64 шестнадцатеричных символа из своего manifest, не на имя файла.
На Windows использую .venv/Scripts/python.exe. DSN передаю внешней переменной;
--dsn-env принимает её имя. Эти команды я пока не выполнял. Генератор и status по ID я написал в CG-105: [WORKBENCH](WORKBENCH.md).

## Пример и вопросы для самостоятельного разбора

На бумаге: attempt A зарегистрирован; в строке 7 нарушен JSON; COPY откатывается;
отдельная транзакция завершает A как quarantined/structural/JSON_SYNTAX/7. Batch
и core отсутствуют, но точные raw-байты доступны. После исправления получаю новый
content и manifest hash, attempt B и новый пакет. Не редактирую диагноз A.

Другой пример: попытка C успела опубликоваться, клиент потерял ответ COMMIT.
Rejection не изменит её терминальный published. Повтор D получает duplicate,
а не вторую оплату. Если соединение журнала тоже недоступно, оставляю честный
unavailable, а состояние C смотрю после восстановления доступа.

Для собеседования: почему попытка не имеет обязательного FK candidate batch_id?
Потому что регистрирую её до появления canonical batch; успешный published_batch_id
уже имеет FK. Почему не храню ошибку в той же транзакции COPY? Rollback удалил бы
её. Почему started не равно failed? Процесс может ещё работать, а исход COMMIT
может быть неизвестен. Почему discovery не чинит всё автоматически? Нужны полный
контракт, блокировки и явный выбор объекта; scan не доказывает отсутствие конкурента.

Наблюдавшихся ошибок работы этого кода нет: я его не запускал. Конкуренцию,
rollback, прерывания, права, Windows/Linux и ограничения времени не проверял.
