# CG-203: карточка, наблюдение и неизменяемая история

Я написал этот срез 25.10.2026, версия `0.1.0.dev8`. Исходники, SQL, команды и
проверки я не запускал. Все примеры ниже объясняют задуманный контракт; фактический
вывод программы и работоспособность я пока не подтверждал.

## Какую задачу я решаю

Я представляю магазин, у которого заказ `O-102` стоит 10000 minor units, а PSP
подтвердил 9000. Отчёт выявляет недостачу 1000. В следующем отчёте оплата может
вырасти до 9500, полностью прийти или снова разойтись. Мне нужна одна карточка
проблемы с объяснимой историей. Создание новой карточки при каждом пересчёте
разбило бы разбор на несвязанные записи. Перезапись старого finding стёрла бы
основание предыдущего решения.

Поэтому я оставляю result каждого run неизменяемым. Карточка хранит текущее
наблюдение, а ревизия связывает изменение с конкретным result. Я не добавляю здесь
назначение сотрудника, комментарии, роли и ручное закрытие: их отдельные контракты
относятся к S4. `workflow_status=open` пока единственное допустимое значение.

## Где я разместил логику

| Файл | Что я в нём делаю | Почему выбрал это место |
| --- | --- | --- |
| `commerceguard/case_projection.py` | Читаю строгую форму finding, воспроизвожу case_key, считаю SHA и выбираю событие | Правило изменения не зависит от соединения с БД |
| `commerceguard/case_store.py` | Применяю run, сериализую запись магазина, читаю список и историю | Транзакция и SQL принадлежат адаптеру хранения |
| `commerceguard/sql/migrations/0006_case_revisions.sql` | Добавляю пять таблиц, FK и запрет изменения истории | Предыдущие опубликованные миграции сохраняю побайтно |
| `commerceguard/__main__.py` | Разбираю `case apply/list/show` | В CLI не переношу правила канонического порядка |

Я не меняю kernel и fingerprint файлов CG-201. Чтение старого результата для
кейсов не требует совпадения с текущими исходниками kernel: результат уже сохранён.
При этом я проверяю его SHA, JSON, cutoff, ruleset и форму findings. Это защита
контракта адаптера, не доказательство правильности предшествующего расчёта.

## Как я определяю актуальный run

Я применяю результат отдельной явной командой. `run execute` не двигает кейсы
автоматически; завершение более медленного исторического расчёта не становится
сигналом заменить актуальное наблюдение.

Мой поток канонических результатов имеет область `merchant_id`. В политике
`canonical-as-was-v1` я принимаю только опубликованный `balance-v1`, `mode=as-was`,
`knowledge_at=as_of`. После первого применения следующий новый run должен иметь
строго больший `as_of`; граница знания не может уменьшаться. Один и тот же уже
применённый run возвращает сохранённую generation и ничего не меняет, даже если
поток успел продвинуться дальше. Это идемпотентность старого retry, а не откат.

Я отказываю разным run с равными временными границами (`CANONICAL_TIME_TIE`).
Случайно выбрать победителя по UUID, времени окончания Python или номеру коммита
было бы скрытым бизнес-правилом. Для более раннего времени возвращаю
`CANONICAL_RUN_REGRESSION`. Отчёт остаётся доступен через `run result/evidence`,
но не меняет карточки. Переключение ruleset требует отдельной миграции смысла.
Коррекции одной старой даты и `as-known-now` я разрабатываю в CG-204 отдельно.

Я предполагаю, что полный OMS snapshot действительно полон, а PSP-пакеты
содержательно достаточны для выбранной границы. Публикация файлов сама по себе
не доказывает внешний watermark провайдера. Поэтому canonical здесь означает
«явно выбран для карточек», а не гарантию полноты внешней финансовой системы.

## Какие данные я сохраняю

| Таблица | Смысл записи |
| --- | --- |
| `ops_case_application` | Неизменяемый факт применения run, generation, predecessor, policy, fingerprint проектора, количества |
| `ops_case_stream` | Единственный текущий run и generation магазина |
| `ops_case` | Стабильная идентичность проблемы, текущая ревизия, присутствие, first/last/evaluated run |
| `ops_case_revision` | Снимок изменившегося finding либо явное отсутствие в конкретном run |
| `ops_case_event` | Причина ревизии: detected, changed, absent или reappeared; пока actor=system |

Я использую прежний `case_key=SHA256(JSON([merchant,order,currency,rule]))`.
Сумма и набор evidence не входят в ключ, но входят в SHA ревизии. Новая сумма
обновляет историю той же проблемы. Другое правило или валюта создаёт другую
карточку. Я проверяю уникальность ключей во всём finding-наборе и не объединяю
повторные строки молча.

`finding_state` принимает `present` и `absent`. Я намеренно не называю отсутствие
`resolved`: ожидание OMS могло измениться, заказ мог исчезнуть из полного снимка,
срок мог быть перенесён. Это изменение наблюдения, не человеческое решение.
Исчезнувшая карточка остаётся в `case list --presence all` и истории. Если finding
вернулся, добавляю `reappeared`; workflow при этом остаётся open.

`first_run_id` я никогда не меняю. `last_seen_run_id` продвигаю только при наличии
finding. `evaluated_run_id` продвигаю при каждом применённом результате, включая
повторное отсутствие. Текущая ревизия может ссылаться на более ранний run, когда
данные finding не изменились. За свежим raw provenance я иду через last_seen run,
за основанием конкретной ревизии — через её run. Это два разных вопроса к истории.

## Как я прохожу через пример

Я начинаю с R1: expected=10000, actual=9000, delta=-1000. Ключ проблемы K создаёт
revision 1, `detected`, present. R2 с теми же значениями и evidence продвигает
evaluated/last_seen, но не создаёт вторую ревизию: шум повторного наблюдения
не скрывает реальные изменения.

В R3 сумма actual=9500. Ключ K прежний, SHA другой: revision 2, `changed`.
Если сумма прежняя, но набор PSP IDs изменился, я также сохраняю changed, потому
что основание цифры существенно для разбора. В R4 расхождения нет: revision 3,
`absent`, finding_json и finding_sha равны NULL. Revision 2 не удаляется.
Если R5 снова содержит K, создаю revision 4, `reappeared`, даже при равенстве
сумм R3. Повтор `case apply R1` после R5 возвращает generation R1 и
`is_current=false`; он не создаёт revision 5.

## Как я провожу транзакцию

Я беру общий lock схемы, читаю опубликованный result и пытаюсь взять отдельный
transaction-level advisory lock магазина. Он сериализует проекцию карточек,
а не блокирует приём новых immutable пакетов. После получения lock мои следующие
READ COMMITTED запросы видят ранее завершённое применение этого магазина.
Занятый lock даёт `CASE_STREAM_BUSY`, без ожидания бесконечной очереди.

Я читаю текущие heads, вычисляю изменения, затем одним COMMIT сохраняю application,
heads, revisions, events и stream. Взаимная ссылка head → revision отложена до
COMMIT, потому что новую карточку и её первую ревизию нельзя вставить одновременно
одной строкой. FK включает presence, поэтому head не может указывать на ревизию
с другим finding_state. Историю защищаю immutable triggers, идентичность карточки —
отдельным guard. Эти правила защищают обычный путь приложения; владелец БД с DDL
доступом всё ещё способен обойти модель.

Обычный отказ откатывает всё применение. При обрыве во время COMMIT я не объявляю
rollback: повторяю тот же run. Если ledger уже сохранился, получаю already_applied.
Отдельного журнала неудачных case-attempt пока нет; журнал выполнения run из CG-202
не выдаю за журнал проекции. Я храню fingerprint двух файлов проектора в application
для объяснения версии, без обещания аттестации загруженного bytecode.

## Параметры для будущего ручного знакомства

Я привожу команды как инструкцию, сам их не выполнял. Нужны отдельная БД,
применённые миграции, принятые синтетические входы и выполненный run из RESULTS.
`RUN_ID` и `CASE_KEY` я заменяю фактическими значениями своего окружения.

```text
python -m commerceguard case apply --run-id RUN_ID
python -m commerceguard case list --merchant demo_shop --presence all --limit 20
python -m commerceguard case show --case-key CASE_KEY --limit 10
python -m commerceguard case show --case-key CASE_KEY --before-revision 10 --limit 10
```

`--run-id` определяет точный result, `--merchant` ограничивает список магазином,
`--presence` выбирает наблюдение, `--limit` ограничивает страницу (1…100),
`--after` продолжает список после case_key, `--before-revision` продолжает историю
к меньшим номерам. В каждой странице списка я возвращаю generation, но не держу
снимок между отдельными запросами. Если generation изменилась, для согласованного
обзора перечитываю список с начала. Я не обещаю стабильный многозапросный export.

Я ограничиваю поток 10000 когда-либо созданными карточками и один finding 64 KiB
canonical JSON. При превышении отказываю всей проекции; история не обрезается.
Результат run при этом остаётся сохранённым. Лимиты времени PostgreSQL не заменяют
измерения производительности; я их пока не проводил.

## Что я предлагаю изменить самостоятельно

1. Я меняю actual в мысленном R3, сохраняя identity. Ожидаю тот же case_key,
   новую revision и changed. Проверку ответа нахожу в `transition` и SHA snapshot.
2. Я делаю R4 и R5 без finding. Ожидаю одну absent revision, новый evaluated run
   и сохранённый last_seen из R3; второй absent не создаёт событие.
3. Я применяю R2 после R5. Если R2 уже был применён, ожидаю noop; если нет и его
   время меньше текущего, ожидаю отказ регрессии. История R5 должна сохраниться.
4. Я проектирую ручное закрытие. Храню workflow отдельно от presence и добавляю
   человеческое событие с основанием. Проверяю дизайн вопросом: может ли простой
   расчёт стереть решение сотрудника? В текущем CG-203 такого действия нет.
5. Я увеличиваю MAX_CASES. Нахожу также SQL counts и документацию; одной константы
   недостаточно. До разрешения исполнения я не называю увеличение безопасным.

На собеседовании я объясню разницу finding/case, порядок событий и времени
завершения, unknown COMMIT, причину deferred FK и отличие absence от resolution.
Для полноценного эксплуатационного вывода мне ещё нужны разрешённые запуски,
проверка конкуренции/сбоев, CG-204 и будущий человеческий workflow.

## Уточнение CG-204

Я оставил исторический as-known-now report-only для Case. Case apply возвращает
CASE_CORRECTION_REPORT_ONLY, пока я не спроектирую отдельное продвижение исторической
корректировки. Новый актуальный as-was может включить поздние данные по своим
границам. Контракт текущего stream не меняю молча. Подробности — LATE_DATA/ADR-25.
