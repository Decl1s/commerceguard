# CG-103: путь от файла до опубликованного пакета

24.10.2026, 0.1.0.dev3. Ни код, ни SQL, ни команды ниже не исполнялись.
Это описание написанного решения и его допущений, без подтверждения поведения.

## Зачем этот срез бизнесу

Аналитик не должен увидеть половину OMS-снимка и принять остальные заказы за
исчезнувшие. Повторная доставка PSP не должна удвоить выручку. Для спорной цифры
нужно найти не только нормализованное событие, но и конкретную строку поступления.
Эти требования определяют транзакцию, identity пакета и таблицу receipts.
UI, сохранённая сверка, карантин и автоматическое восстановление здесь не добавлены.

## Четыре hash и два UUID

content_sha256 относится к точным байтам входа, включая BOM и line endings.
record_sha256 относится к тексту логической записи после начального UTF-8 BOM,
но с сохранёнными окончаниями строк. semantic_sha256 описывает бизнес-смысл.
manifest_sha256 — новый четвёртый hash: весь нормализованный envelope, включая
source, merchant, contract version, content hash, counts и времена.

Канонизация manifest: поля сортируются, JSON компактный ASCII, даты приведены
к UTC с шестью знаками микросекунд и Z, завершение ровно одним LF. LF входит в hash.
У PSP отсутствуют effective_at/is_complete, у OMS они присутствуют. Исходные
пробелы manifest не сохраняются; данные сохраняются побайтно. Подписи источника
здесь нет: совпадение hash означает совпадение содержимого, не его достоверность.

batch_id — UUIDv5 в NAMESPACE_URL от строки commerceguard:batch:v1: и manifest hash.
snapshot_id использует другой префикс commerceguard:oms-snapshot:v1:.
UUID здесь детерминированная ссылка, не секрет, не подпись и не замена SHA-256.
Машинный адрес не используется. При теоретической коллизии UUID вставка отклонится
по PK; пакет не присваивается существующему без проверки полного envelope.

Почему нельзя оставить UNIQUE merchant/source/content hash из 0001? Два полных
OMS-снимка могут иметь одинаковые строки, но разные effective_at. Это две версии
ожиданий, а один физический raw-объект можно переиспользовать. 0002 заменяет уникальность
на manifest_sha256 и не изменяет уже версионированный SQL 0001. Новые NOT NULL поля
неоткуда честно получить у вручную вставленных legacy-пакетов: при непустом старом
ingest_batch миграция отказывает. Автоматического удаления или выдуманного backfill нет.

## Что хранится на диске

Raw root по умолчанию workspace/raw, можно явно выбрать --raw-root. Непустой
чужой каталог без собственного маркера .commerceguard-raw-v1 не присваивается.
Пути не строятся из manifest или исходного имени:

```text
objects/<первые 2 символа content hash>/<content hash>
manifests/<первые 2 символа manifest hash>/<manifest hash>.json
```

В БД сохраняются только относительные ключи. Перенос raw root целиком не требует
переписывания абсолютных путей в фактах. Root — каталог под контролем пользователя;
конкурентный враждебный процесс с правом менять родителей каталогов не моделируется.
Конечные symlink и ссылки внутри создаваемой структуры отклоняются. Нельзя направлять
другие программы на запись в этот каталог: это протокол immutable-by-convention,
не WORM-носитель и не защита от администратора машины.

Установка объекта: собственный временный файл в целевом каталоге, ограниченное
копирование, повторный size/hash, flush/fsync, закрытие, os.link на окончательное
имя. Hard link создаёт готовый объект без перезаписи. Уже существующий объект
проверяется целиком; неверные байты вызывают RAW_CORRUPT, а не «починку» поверх истории.
Нужен filesystem с поддержкой hard links, например локальные ext4/NTFS; сетевые
диски, FAT и облачные папки не объявлены поддержанными. Переносимого запасного
алгоритма с более слабой атомарностью нет. После аварийного завершения могут остаться
.pending-файлы; автоматическое удаление сейчас не реализовано.

fsync файла уменьшает риск потери байтов; на POSIX также синхронизируются каталоги.
Абсолютная гарантия при отключении питания, особенно на Windows/сетевом носителе,
не заявляется. Это не резервная копия и не шифрование. Свободное место требуется
для фиксированной временной копии, raw, временной установки и PostgreSQL/WAL.

## Публикация по шагам

1. Manifest проходит строгий CG-102 контракт. Данные целиком фиксируются в
   TemporaryFile и сверяются с заявленными hash и размером.
2. Raw-sink сохраняет данные, затем canonical manifest. Ошибка на этом шаге
   не приводит к подключению БД. Raw может сохраниться даже у синтаксически плохих строк.
3. Открывается одно соединение с autocommit=True и явный transaction().
   READ COMMITTED, UTC, connect timeout 5 s, lock timeout 5 s,
   statement timeout 120 s, idle-in-transaction timeout 30 s. Это пределы отдельных
   серверных действий, не обещание длительности всей обработки файла.
4. Shared transaction advisory lock общего ключа исключает наш мигратор.
   Exclusive bigint lock по SHA-префиксу merchant сериализует OMS/PSP одного магазина.
   Try-lock отказывает сразу; hash-коллизия лишь излишне сериализует два магазина.
   Эти locks действуют только между сотрудничающими клиентами; DBA не связан протоколом.
5. Проверяются БД commerceguard, PostgreSQL 16, owner/identity и полная версия схемы.
   Ingest не запускает миграции сам. Создаётся TEMP stage с ON COMMIT DROP.
6. COPY FROM STDIN принимает типизированные кортежи через write_row. Нет серверного
   пути, PROGRAM, интерполяции пользовательских значений или самодельного CSV escaping.
   Raw и нормализованные поля идут одной COPY-сессией; одновременно открывать две нельзя.
7. Parser обязан дойти до EOF и объявленного row_count. Сверяется COUNT staging.
   Даже известный пакет полностью проходит этот путь: наличие hash в БД не заменяет
   валидацию предъявленного файла.
8. Точный опубликованный manifest возвращает duplicate_batch=true без новых строк.
   Метаданные сверяются полностью. Существующий неопубликованный пакет вызывает отказ;
   «доделать наугад» нельзя. Это граница будущего CG-104.
9. Для нового PSP определяются semantic/temporal конфликты, затем записывается batch,
   весь raw, snapshot/новые факты и receipts. Состояния received → staged → published
   меняются внутри одной транзакции; снаружи промежуточные состояния не видны.
10. Счётчики и published_at записываются до COMMIT. JSON-успех возвращается после
    подтверждения COMMIT, не после окончания COPY. TEMP-таблицы исчезают.

## Повтор события и повтор пакета

Внутри нового PSP-пакета две записи с одним ID и смыслом дают две raw-строки,
два receipt, один факт. Каноническая запись выбирается по минимальному observed_at,
при равенстве — по минимальному ordinal. Её raw-ссылка соответствует именно ей.
semantic hash намеренно не включает observed_at; полный бизнес-payload также
сравнивается с сохранённым фактом, чтобы не доверять одному hash.

Если событие уже опубликовано, равное или более позднее observed_at даёт receipt
к прежнему факту. Более раннее observed_at вызывает TEMPORAL_CONFLICT всего пакета.
Изменённые сумма, заказ, валюта, kind или occurred_at вызывают PSP_CONFLICT.
UPDATE канонического observed_at не выполняется: иначе прошлый отчёт незаметно
начнёт видеть факт раньше. Отдельный контракт исторических исправлений — будущая работа.

Учебный пример на бумаге: строки E01@10:00, E01@10:05, E02@10:06 дают N=3,
unique=2, duplicates=1. Если E01 уже сохранён с тем же смыслом и observed=10:00,
то new_facts=1, known_events=1, duplicate_rows=1; receipts добавится три.
Равенство new+known+duplicates=N закреплено CHECK опубликованного batch.
При повторе всего того же manifest raw_rows_inserted/new_facts/known_events=0:
это действия текущего вызова, а rows_parsed/duplicate_rows — свойства входа.

## Сбои, границы и продолжение

Ошибка parser, COPY, FK или конфликта прерывает транзакцию. До COMMIT читатели
не получают часть нового snapshot; прежний опубликованный core остаётся.
Raw и canonical manifest при этом могут остаться без batch: файл и БД не одна
транзакция. При обрыве связи во время COMMIT результат неизвестен: возможны и
фиксация, и откат. Повторяется тот же manifest; нельзя генерировать новую identity
лишь потому, что ответ клиенту не пришёл. В CLI скрыты server DETAIL и payload.

Сейчас не записываются failed/quarantined партии отдельной транзакцией, нет списка
orphan, restart/recovery команды и очистки. Это следующий CG-104. Нет постоянного
выбранного канонического run: S2 должен заморозить входные batch IDs и knowledge cutoff.
Источник observed_at и технические received_at/published_at — разные времена;
одного фильтра observed_at недостаточно для исторического «как система знала тогда».

## Параметры для самостоятельного запуска позже

Разработчик это не выполнял; пользовательское ограничение исполнения не меняется.
После самостоятельной подготовки драйвера, БД и явного db migrate:

```bash
.venv/bin/python -m commerceguard ingest publish --manifest workspace/input/oms.manifest.json --data workspace/input/oms.csv --raw-root workspace/raw
```

В PowerShell Python заменяется на .venv/Scripts/python.exe. --manifest — envelope,
--data — отдельно выбранный файл, --raw-root — каталог объектов, --dsn-env — только
имя внешней переменной DSN (по умолчанию COMMERCEGUARD_DATABASE_URL). Никаких паролей
в Git или аргументах. Команда печатает ID, hash, относительные ключи и счётчики,
не строки платежей. Синтетический генератор и status по партии остаются CG-105.
